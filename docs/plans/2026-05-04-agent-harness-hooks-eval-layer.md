# Lock down the agent harness: deterministic hooks + observability for the Telegram MCP front door

**Sources:**
- https://medium.com/@Micheal-Lanham/building-agents-in-2026-why-the-harness-matters-more-than-the-model-eb72448fee04 — Lanham. Conceptual frame: five-layer roadmap (Persona / Tools / Reasoning / Memory / Evaluation) and the claim that the agent line sits in the harness, not the model. Identifies Evaluation/Feedback as the layer minimal demos skip and production agents need.
- https://medium.com/data-science-collective/claude-code-hooks-explained-the-missing-layer-between-prompts-and-production-d0e3d1509278 — Parreño. Concrete mechanism in Claude Code: hooks (`SessionStart` / `PreToolUse` / `PostToolUse` / `Stop` / `TaskCompleted`) turn prose-rules into deterministic enforcement. Event → matcher → structured input → handler.

**Project:** reels-digest-agent (Telegram FastAPI lives here; Claude-Code-side hook config lives in `~/.claude/settings.json` but the observability + eval surface lands in this codebase).

**Created:** 2026-05-04

## What you already have

- **Persona layer (✓):** `~/.claude/rules/jarvis-persona.md` is the role/voice spec for Telegram-channel turns. Standing context + recent thread + open promises in `~/.claude/jarvis/state.md` (read-on-entry / update-on-exit, prose-enforced).
- **Tools/Actions layer (✓):** `~/.claude/rules/telegram-handlers.md` Patterns A–J map intents → backend actions. MCP tools registered: telegram, github, context7, playwright, sequential-thinking. FastAPI server on `localhost:8000` with `/api/reel`, `/api/article`, `/api/transcribe`, `/api/status`. Bearer auth, idempotent dispatch.
- **Reasoning layer (✓):** `~/.claude/rules/data-routing.md` is the dispatch table; `CLAUDE.md` Tool Selection Hierarchy gates Sequential Thinking / Context7 / brainstorm-vs-plan. Pattern B step 9 includes a non-trivial "merge or create" decision.
- **Memory layer (✓):** Three tiers — `~/.claude/memory/` (identity, active-context, decisions), `~/projects/brain/` (graphified knowledge + wiki layer), per-project `docs/project_notes/` (scaffolded by `/project-memory` skill, piloted on this repo). Logging in `src/server.py` is structured Python logging.
- **Evaluation layer (✗ — the gap):** No traces, no eval table, no graders. `recap.py` reports `pending/done/error` reel counts but nothing about pattern dispatch quality (did Whisper transcribe correctly? did Pattern B's analysis pass actually write a plan? did Jarvis update state.md when it should have?). The `~/.claude/hooks/` folder exists but is empty with a "Phase 4 deferred" README. `~/.claude/settings.json` has no `hooks` key. Every behavioural rule (`security.md` "NEVER rm -rf without confirmation", `git.md` "never --no-verify", jarvis-persona "update state.md on exit") is enforced *probabilistically* by Claude reading the rule, not deterministically by the runtime.

## What the articles propose

- **Lanham:** the agent line sits in the harness's permission surface and iteration budget, not the model. Five layers; Evaluation is what production-grade agents add. GAIA leaderboard shows the same Claude Sonnet 4.5 scoring 74.55% in HAL Generalist vs 30.91% in HF Open Deep Research — same model, different harness, 44-point spread. "Pick evaluation metrics before you pick a benchmark."
- **Parreño:** Claude Code hooks fire on lifecycle events with structured input. Five events worth knowing first: `SessionStart`, `PreToolUse`, `PostToolUse`, `Stop`, `TaskCompleted`. Handlers can be `command` (shell), `http`, `prompt`, or `agent`. Matchers narrow the trigger (e.g. `Edit|Write` only). Hooks live in `settings.json` at user / project / managed scope. Critical move: any rule that's currently in CLAUDE.md prose should be re-asked: *does this belong in the model's judgement or the harness's enforcement?*

## Gap (where this extends what you have)

The user's setup already has 4 of Lanham's 5 layers. The missing one — Evaluation/Feedback — is also where Parreño's hooks land most usefully. Right now: (a) destructive Bash patterns (`rm -rf`, `git push --force`, `--no-verify`) are blocked by prose, not by the runtime; (b) the jarvis-persona "update state.md on exit" instruction has no enforcement, so a turn can end without the recent-thread line being written; (c) every Telegram pattern dispatch is invisible after the fact — no record of "what intent → which pattern → succeeded?" beyond ad-hoc Python logs in `server.py`. Closing the gap means: (1) un-defer the `~/.claude/hooks/` folder, install a small set of `PreToolUse` deterministic blocks for the durable safety rules, (2) add a `harness_events` table in the reels-digest-agent SQLite and a tiny logger that the FastAPI endpoints + (eventually) hook scripts both write into, (3) surface the eval signal in `recap.py` so the daily recap reports harness health, not just reel counts.

## Plan

1. **Decide what's deterministic vs probabilistic.** Read `~/.claude/rules/security.md`, `git.md`, `jarvis-persona.md`, and `telegram-handlers.md` end-to-end with one question: *if this rule failed silently, would the user notice?* Tag each rule with `[hook]` or `[prose]`. Likely deterministic candidates: rm -rf without confirmation, force-push to main, --no-verify, --no-gpg-sign, editing settings.json without explicit ask, jarvis state-update-on-exit. Likely probabilistic-and-fine: voice tone, length discipline, "anticipatory framing." The audit goes in `~/projects/reels-digest-agent/docs/decisions/2026-05-04-rules-as-hooks-tagging.md` (one decision record so the tagging is reviewable).
2. **Un-defer `~/.claude/hooks/`.** Replace the README's deferral note with a real index pointing to each script. Create `~/.claude/hooks/scripts/` for handler scripts, all bash + jq, no Python deps so they stay portable.
3. **First three hooks — narrow, high-value, easy to debug.** Add to `~/.claude/settings.json` under a new `hooks` key:
   - **`PreToolUse` matcher `Bash`** → script reads structured input on stdin, greps the command for danger patterns (`rm -rf /`, `rm -rf $HOME`, `git push.*--force(?!-with-lease)`, `git reset --hard`, `--no-verify`, `--no-gpg-sign`, `dropdb`, `DROP TABLE`). Exit 2 with a JSON `permissionDecision: "ask"` reason — Claude shows the prompt to the user. This is the "promote prose rule to runtime" piece.
   - **`PostToolUse` matcher `Edit|Write` on `~/.claude/jarvis/state.md`** → log the diff to `~/.claude/hooks/logs/jarvis-state-changes.log` so we can see when state.md actually moves and audit drift.
   - **`PostToolUse` matcher `mcp__plugin_telegram_telegram__reply`** → POST a one-line event to `http://localhost:8000/api/harness-event` with `{type: "telegram.reply", text_len, chat_id, ts}`. Single source of truth for what the bot actually said.
4. **Add the eval table.** Migrate `dev.db` (or `data/db.sqlite` — verify which the project uses) with a `harness_events` table: `id`, `ts`, `source` ('telegram-pattern' | 'hook' | 'fastapi'), `kind` (event name), `payload_json`, `outcome` ('ok'|'error'|'blocked'). Add a `POST /api/harness-event` endpoint to `src/server.py` that's bearer-auth-gated and writes to that table. This is the "single drain" both the hooks and the FastAPI handlers write into.
5. **Backfill from the existing logs.** `src/server.py` already logs `POST /api/reel → <action> <id>` etc. via `logger.info`. Add inline calls to the new logger right before each `logger.info` so we double-write into both stdlib logging and the events table. Keep the stdlib logs — they remain the canonical line-oriented log; the events table is the queryable surface.
6. **Surface harness signal in recaps.** Extend `src/recap.py` so the morning + evening recap includes a "Harness today" line: `N pattern dispatches (X reels, Y articles, Z transcripts), W blocked by hooks, V state-changes`. Today the recap mentions reel queue counts and unchecked todos; this adds one more block above them. Failure mode: zero events → skip the block silently, don't fabricate.
7. **Eval pass on Pattern B's analysis step.** Pattern B step 9 is the most judgement-heavy step in the harness ("does this article merge with an existing plan, or is it a new file?"). Add a follow-up `prompt`-type hook (per Parreño's advanced section) that runs after Pattern B writes a plan, asking: *"Does this plan exist as a separate file when it should have merged, or vice versa? Reply with merge-violation, fragment-violation, or ok."* Log the verdict to `harness_events`. We don't auto-correct on violation — surface it in the recap and let the user judge.
8. **Stop here. Don't pre-build hooks for things that aren't biting yet.** Skip `TaskCompleted` patterns, multi-agent coordination hooks, MCP-event hooks. The decision rule from step 1 is the gating mechanism: a hook only earns its place if the prose rule is currently failing silently and the failure has a real cost. Re-run step 1 quarterly.

## Notes on safety + reversibility

- Every hook ships with an off-switch: a `~/.claude/hooks/disabled` file the scripts check first. Touch the file and all hooks become no-ops — useful when debugging Claude Code itself.
- Don't put hooks behind sudo or anything that mutates outside `~/.claude/` and `~/projects/reels-digest-agent/`. The hooks article warns against this, and the user's `security.md` already gates "modifying system files."
- Test each hook standalone with a hand-crafted JSON input on stdin before wiring it into `settings.json`. Parreño's article is explicit: "knowing the structure is still important, because you need to be able to evaluate what Claude produced."
- The `command` hook variant first; only escalate to `prompt`/`agent` hooks for step 7 (where semantic judgement is the point).
