# Decisions

ADR-style log of architectural decisions specific to `reels-digest-agent`. Append-only; never edit or delete past entries — if a decision is reversed, add a new entry explaining why.

User-scope decisions that apply to every project belong in `~/.claude/memory/decisions.md`. This file is for choices that only make sense in the context of this codebase.

## Format

```
## Short title
- **Decision**: what we chose.
- **Context**: what was going on / what problem prompted this.
- **Alternatives**: what else was on the table and why it was rejected.
- **Consequences**: what this commits us to, what it rules out, what it makes harder later.
- **Date**: YYYY-MM-DD.
```

## Entries

## Claude vision (not Tesseract) for reel OCR and carousel handling
- **Decision**: Pass video keyframes (3 per video, ffmpeg) and carousel images (yt-dlp, as-is) directly to Claude Sonnet 4.6's vision API alongside the audio transcript. No standalone OCR step. Cap at 6 images per post to bound vision-token cost. Lives in `src/visual_extractor.py`, called from `src/daily_job.py`.
- **Context**: Reels routinely carry stylized text overlays (prompts, captions, lists), and many posts are image-only carousels with no audio. The previous pipeline only transcribed audio via Whisper, so on-screen text and image-only posts were invisible to the summary.
- **Alternatives**: (a) Tesseract OCR locally — free but poor on stylized fonts, animated overlays, non-Latin scripts; (b) hybrid Tesseract + Claude vision — extra moving part with no clear quality win; (c) skip image-only carousels — user-rejected.
- **Consequences**: Tighter summaries (vision describes the frame, not just OCR text), one fewer dependency. Vision cost ~3-5× per reel; the cap on 6 images per post is the bound. If cost ever bites, the lever is fewer keyframes or smarter frame selection — not switching backends.
- **Date**: 2026-04-29

## /api/reel idempotent with action-coded response
- **Decision**: `POST /api/reel` is idempotent and returns `{"status": "<action>", "id": "<reel_id>"}` where action ∈ `{queued, requeued, already_pending, already_done}`. Error rows auto-reset to pending on resubmit; done and pending rows are no-ops. `db.add_reel(url)` returns the action tuple.
- **Context**: Reels are deduped by SHA-256 of the URL. The original endpoint silently no-op'd on every conflict, including error rows, leading to a stuck-state bug (see `bugs.md` 2026-04-29).
- **Alternatives**: A separate `/api/retry` endpoint would split error-recovery from the happy path and require Telegram-side logic to know which to call. Combining them on `POST /api/reel` keeps one entry point and makes error recovery automatic on resend.
- **Consequences**: Every caller (Telegram MCP front door, iOS Shortcut, web UI) can render an honest confirmation. Adds one tuple unpack to `db.add_reel` and one switch in Pattern A. No new endpoints, no migration.
- **Date**: 2026-04-29

## Playwright-rendered article fetcher with browser-imported Medium session
- **Decision**: `/api/article` routes every URL through headless Chromium (`src/generic_article_fetcher.py`). Medium URLs ride a logged-in session captured by exporting cookies from the user's real browser via Cookie-Editor and converting to Playwright's `storage_state` (`scripts/import_medium_cookies.py`). For non-`medium.com` URLs whose slug ends in a 12-char hex post ID, the fetcher additionally tries `https://medium.com/p/<id>` and uses whichever returns >1.5× more body content. Extraction is `<article>`-tag-first via `_extract_article` from `article_fetcher.py`, with readability-lxml as fallback only when body < 1500 chars.
- **Context**: The original HTTP+sid+BeautifulSoup path 403'd on member-only stories even with a fresh sid; custom-domain Medium publications returned only cookie banners; a headed Playwright login script was blocked by Cloudflare due to headless-shell fingerprint tells. See `bugs.md` 2026-04-30.
- **Alternatives**: (a) Maintain a parallel HTTP path for non-Medium URLs — rejected as duplication; (b) automate the Medium login inside Playwright — rejected, Cloudflare detection is upstream of any flag we can flip.
- **Consequences**: 3-5s render cost per article (acceptable at personal-use volume). Storage_state file lives at `data/medium_storage_state.json` (gitignored), regenerated when Medium invalidates the session. The old `src/article_fetcher.fetch_article` HTTP path is no longer called; the module is imported only as a library (`_extract_article`, `_HEADERS`, helpers).
- **Date**: 2026-04-30

## Article and reel auto-planning pass
- **Decision**: Every article URL sent via Telegram and every reel processed by the daily digest triggers a planning pass. Output is a markdown plan with fixed structure (`# topic / **Source(s)** / **Project** / **Created** / ## What you already have / ## What the article (or reel) proposes / ## Gap / ## Plan`) saved to `<matched-project>/docs/plans/<YYYY-MM-DD>-<slug>.md` or `~/projects/_inbox/<YYYY-MM-DD>-<slug>/PLAN.md`. A pointer line is appended to `data/todos.md` under `## Plans (from articles + reels)`.
- **Context**: User framing: "every article I send is something I want to work on — by the time I sit down at the keyboard, the plan should already be there." Reels follow the same logic — a Notion summary is reference material, but a stack-tied plan is actionable.
- **Alternatives**: (a) Unified backend service that both sides call — rejected because article handling already runs in the Claude session with all memory loaded; going through an API would add latency and lose context. (b) On-demand planning ("plan this one") — rejected, user wants auto on every share; the recap surface doubles as a pruning mechanism (uninteresting plans get ticked off without execution).
- **Consequences**: Two implementations to maintain (Claude in-session for articles via Pattern B; Python+Anthropic SDK for reels via `src/reel_planner.py`). Failure-isolation per-side. Reel-side same-topic merge is deferred until same-topic reels actually pile up.
- **Date**: 2026-04-30

## Instagram cookies for yt-dlp + caption fallback for image-only carousels
- **Decision**: yt-dlp gets a Netscape-format cookie file (`data/instagram_cookies.txt`, gitignored, mode 600) loaded from `INSTAGRAM_COOKIES_FILE` in `src/config.py` when present. Cookies are exported via Cookie-Editor on instagram.com (JSON format) and converted by `scripts/import_instagram_cookies.py`. When audio download AND visual extraction both yield nothing (image-only carousels — yt-dlp's Instagram extractor returns 0 image URLs even with auth), `src/daily_job.py` calls `src.downloader.fetch_caption(url)` and uses the post caption as the textual signal for `summarize()`.
- **Context**: Two reels on 2026-05-06 (`7f11cf9b4c71`, `81b67c06b1c9`) failed with empty content. Diagnosis: cookieless yt-dlp hits Instagram's "Requested content is not available, rate-limit reached or login required" wall on gated posts, and even with cookies, the Instagram extractor returns no `formats` or `thumbnails` for image-only carousel slides. The post HTML is JS-rendered, so plain-`requests` scraping doesn't see image URLs either.
- **Alternatives**: (a) Persistent Playwright browser profile signed into Instagram — rejected by user due to ban risk on their main account. (b) Direct GraphQL hits against Instagram's web API — fragile, breaks on payload shape changes, looks more bot-like than yt-dlp + cookies. (c) Add Instaloader as a dependency for image extraction — rejected for now, adds dep + maintenance burden when caption-only solves both observed cases. (d) Skip image-only carousels entirely and notify — leaves substance on the floor when captions are rich.
- **Consequences**: yt-dlp now requires a fresh cookie export when Instagram invalidates the session — `data/instagram_cookies.txt` is the single source of truth, regenerated by re-running `scripts/import_instagram_cookies.py` on a fresh JSON export. Caption-only summaries are thinner than full image summaries — for caption-rich posts (suraj.dsgn's "5 Sites for Vibe Coders") the result is good; for caption-poor CTA posts (chase.h.ai's "Comment 'agency' to get the skill pack") the summary correctly captures that it's a CTA but has no substance to extract. Closing the image-extraction gap (Instaloader, GraphQL, or Playwright) is deferred until caption-poor carousels with substantive slide content actually pile up.
- **Date**: 2026-05-06

## Scrapling fast tier in front of Playwright for non-Medium URLs
- **Decision**: `fetch_generic_article` tries `src.scrapling_fetcher.fetch_with_scrapling` first for any URL that isn't Medium-family. If Scrapling returns content_md ≥ 1600 chars, return it; otherwise fall through to the existing Playwright path. Medium-family detection (medium.com host OR 12-char hex post ID in slug) routes straight to Playwright since neither cookie injection nor the canonical-medium.com/p/<id> retry trick are reproducible without a real browser. Every fetch (Scrapling, Playwright, Playwright+readability) writes one JSONL line to `data/fetch_log.jsonl` via `log_fetch()`.
- **Context**: `/api/article` is the single biggest latency contributor when the user shares a non-Medium URL via Telegram. Plan: `docs/plans/2026-05-04-article-fetcher-optimization.md`. Phase 0 baseline (10-URL benchmark, `scripts/benchmark_urls.txt`): p50 14s, p95 37s — Playwright pays a full Chromium launch on every request. Phase 1 swap-in: 3/3 plain non-Medium URLs returned ≥1500 chars in <2s with Scrapling, satisfying the wiring threshold from the plan.
- **Alternatives**: (a) Replace Playwright entirely with Scrapling — rejected; custom-domain Medium publications (`ai.plainenglish.io`, `levelup.gitconnected.com`) only return ~3KB stubs from Scrapling vs ~50KB via Playwright's canonical-medium.com retry. (b) Use Scrapling only as a fallback after Playwright failure — rejected; that's the inverse of what we want, since Playwright is the slower path. (c) Demote Scrapling to extraction-only on Playwright HTML — rejected at this stage because the speed win comes from skipping the browser launch entirely; revisit if Cloudflare bypass proves unreliable in soak.
- **Consequences**: New runtime dependency `scrapling[fetchers]>=0.4.7` (pulls in `curl_cffi`, `patchright`, and forces Playwright to ≥1.58 — the existing browser cache had to be re-downloaded via `playwright install chromium`). On the benchmark suite: paulgraham.com 3561ms→673ms (5.3×), overreacted.io 25994ms→985ms (26×). Medium-family URLs unchanged. The threshold (1600 chars on `content_md`) accounts for the ~100-char header (title + author + source); raw body threshold equivalent is ~1500. Scrapling's StealthyFetcher is wired but only fires on Cloudflare interstitials — its slower path (5–10s) hasn't been exercised on real traffic yet. 48h soak still pending — the values in `key_facts.md` are bench-only, not production-observed.
- **Date**: 2026-05-06

## Phase 2 of article-fetcher-optimization (Vercel Agent Browser) deferred
- **Decision**: Phase 1 (Scrapling fast tier) shipped 2026-05-06. Phase 2 (Vercel Agent Browser MCP swap) is deferred — closed without integration.
- **Context**: The plan's premise was that Vercel AB exposes an MCP server interface so it could replace the Playwright MCP in `~/.claude/settings.json`. Investigation found that `vercel-labs/agent-browser` ships a Claude Code *skill* (`npx skills add vercel-labs/agent-browser`), not an MCP server. The community `agent-browser-mcp` wrapper exists but is third-party. Plan stop condition triggered: "If Phase 2 step 9 shows Vercel AB has no MCP interface, defer Phase 2."
- **Alternatives**: (a) Adopt the official skill route — viable but the plan was MCP-shaped; the skill story deserves a fresh plan. (b) Use the community MCP wrapper — additional trust surface, third-party. (c) Build out the integration despite the stop condition — rejected as plan-deviation without clear payoff signal.
- **Consequences**: Phase 2 is not closed forever; pickup point is "after a real soak of the new Scrapling-first fetcher and observation of which Jarvis sessions actually burn tokens on browser screenshots." If/when revived, the plan needs rewriting around the skill path. No code, no settings change.
- **Date**: 2026-05-07

## Two-phase reel planner with executor/advisor model tiering
- **Decision**: Reel planning is split into two Anthropic SDK calls behind `src/model_router.py`. Phase 1 (`call_executor`, default `claude-haiku-4-5`) classifies the reel into `matched_project` + `topic_slug` from a stable hint map — no active-context dump in this prompt. Phase 2 (`call_advisor`, default `claude-sonnet-4-6`) takes the classification + full active-context + reel summary and writes the plan markdown. Both calls log per-call cost (`model`, `label`, `input_tokens`, `output_tokens`, `latency_ms`) to `data/cost_log.jsonl` via `model_router.log_cost`. `summarizer.py` (the multimodal vision call) keeps its own client because of custom params (`thinking={"type": "disabled"}`, `output_config={"effort": "low"}`) but reuses `log_cost` so the cost log stays single-source-of-truth. Models are swappable via `EXECUTOR_MODEL` / `ADVISOR_MODEL` env vars.
- **Context**: Plan: `docs/plans/2026-05-04-claude-code-dual-agent-haiku-opus-cost-reduction.md`. Pre-tier baseline: every reel plan was one Sonnet call (~5K in, ~1.5K out). Per-reel cost on the new pattern (smoke test): Haiku classify 323/43 tokens, Sonnet synthesize 4669/1114 tokens. Sonnet token usage is roughly the same as before because the synthesis prompt still carries the active-context block; the win is the cheap classification offload (~17% per-reel cost reduction at current Sonnet-vs-Haiku pricing) plus a reusable cost-logging surface for future tiering decisions.
- **Alternatives**: (a) Push the summarizer to Haiku as well — rejected for now because Haiku vision quality on stylized text overlays (the original reason Sonnet vision replaced Tesseract per `decisions.md` 2026-04-29) is unverified; revisit if the cost log shows summarizer dominating. (b) Use Opus for the advisor — rejected as overkill for personal-volume reel planning; Sonnet 4.6 handled the smoke test plan well. (c) Move classification into a deterministic Python regex (no LLM) — rejected because the hint map is fuzzy and the classifier sometimes needs to read the summary, not just the title.
- **Consequences**: New module `src/model_router.py` is now the canonical entry point for SDK calls in this repo; new code should go through it instead of instantiating `Anthropic()` directly. `data/cost_log.jsonl` is the queryable cost-vs-quality surface — recap script could surface daily totals as a future extension. Pattern documented in `~/.claude/memory/system-patterns.md` so future projects reuse it. The "60-70% cost reduction" claim from the source reel doesn't apply directly because reel-planner work is mostly synthesis (Sonnet-tier), not mechanical execution (Haiku-tier); larger savings would require shifting more work to the executor tier in future code.
- **Date**: 2026-05-07

## Agent harness: deterministic enforcement layer + harness_events ledger
- **Decision**: Plumbed in the missing Evaluation/Feedback layer from the Lanham five-layer model. Three things shipped together: (a) a `harness_events` SQLite table + `add_harness_event()` helper + `harness_events_since()` query in `src/db.py`, plus a bearer-auth `POST /api/harness-event` endpoint in `src/server.py`; (b) the existing endpoints (`/api/reel`, `/api/article`, `/api/transcribe`) write a row to harness_events alongside their stdlib log line; (c) four Claude Code hooks under `~/.claude/hooks/scripts/` wired in `~/.claude/settings.json`. Hooks: `bash-danger-check.sh` (PreToolUse Bash, danger-pattern grep returns `permissionDecision: ask`), `jarvis-state-log.sh` (PostToolUse Edit|Write filtered to `~/.claude/jarvis/state.md`, observe-only log to `hooks/logs/jarvis-state-changes.log`), `telegram-reply-event.sh` (PostToolUse `mcp__plugin_telegram_telegram__reply`, best-effort POST to /api/harness-event), `plan-write-event.sh` (PostToolUse Edit|Write filtered to `**/docs/plans/*.md` and `**/_inbox/**/PLAN.md`, logs `plan.written` events). Each hook checks for `~/.claude/hooks/disabled` and no-ops if present (the off-switch). Recap (`src/recap.py`) gets a "Harness (last 12h)" block above the queue counts; silently skipped when there are no events. Audit doc: `docs/decisions/2026-05-04-rules-as-hooks-tagging.md`.
- **Context**: Plan: `docs/plans/2026-05-04-agent-harness-hooks-eval-layer.md` (Lanham + Parreño). Pre-state: every behavioural rule (`security.md` "destructive commands," `git.md` "never force-push to main," jarvis-persona "update state.md on exit") was prose-only — Claude reading the rule was the only enforcement. Pattern dispatches were invisible after the fact; only stdlib logs in `server.py` recorded them. The audit tagged each rule `[hook]` or `[prose]`; v1 implements the three highest-value `[hook]` candidates. Slight deviation from the plan: hooks use `bash + python3` instead of `bash + jq` because `jq` isn't installed on this WSL system and `python3` is preinstalled — same portability story without a sudo install. Documented in `~/.claude/hooks/README.md`.
- **Alternatives**: (a) Hold off on hooks and just add the harness_events ledger — rejected because the prose-rule "would silent failure be visible?" question already had real answers (force-push to main, no-verify commits, Jarvis state-update misses); the audit listed concrete cases. (b) Implement Parreño's prompt-type hook for Pattern B merge-vs-fragment violations — deferred (plan step 7 stretch goal). The simpler `plan.written` row is the foundation; the LLM-grader can attach later. (c) Use the `command` hook variant only — adopted; no `prompt`/`agent` hooks in v1 because they require more research on output contracts.
- **Consequences**: All four hooks are off-switchable via a single `touch ~/.claude/hooks/disabled` command — useful when debugging Claude Code itself or when a hook regresses. New behavioural rules get tagged in the audit doc and the audit re-runs quarterly (next: 2026-08-07). The harness_events table is a queryable signal surface: recap surfaces the last-12h roll-up; ad-hoc queries can answer "did Pattern B fire after that voice note last Tuesday?" without grepping logs. Hook activation: hooks fire from the next Claude Code launch, not the current session — settings are read at startup. The current session's behaviour is unchanged.
- **Date**: 2026-05-07

## Same-topic article plans merge in place
- **Decision**: When an incoming article overlaps an existing plan in the matched project's `docs/plans/`, extend the existing plan in place: promote `**Source:**` to `**Sources:**` (plural), add the new URL with a one-line tag for what it uniquely contributes, fold specifics into existing sections (preferring the more concrete version), insert any new step at the right ordinal in `## Plan`, keep filename and `**Created:**` date. Don't fragment same-topic plans into multiple files. Reel-side merge is NOT implemented.
- **Context**: In one session the user shared three articles; two were the same architectural pattern (self-maintaining wiki for `~/projects/brain/`). Without a merge rule, each share would have created its own file. User: "if articles are the same topic, just make it into one plan by using the best case for my projects from both."
- **Alternatives**: Always create a new file with `-2`/`-3` suffix — rejected as fragmentation. Defer to user to merge manually — rejected, defeats the auto-planning value.
- **Consequences**: One plan per topic per project. `todos.md` pointer never breaks (filename preserved). Slug-collision suffix rule still applies for genuinely different topics that happen to slugify identically. Reel-side merge is the obvious next extension — non-trivial because it requires passing existing plans into the Python prompt.
- **Date**: 2026-04-30

## Claude Code MCP plugin is the Telegram front door; the long-polling Python bot is dead
- **Decision**: When the user sends Instagram reel or Medium article URLs through their Telegram bot, Claude (running as the `plugin:telegram:telegram` MCP consumer) detects the URL and dispatches to this FastAPI backend. The legacy long-polling Python handler (`src/telegram_bot.py`) is intentionally dead and must not be re-enabled — its long-polling grab on the bot token would conflict with the MCP plugin and silently steal incoming messages. Routing rules live in `~/.claude/rules/telegram-handlers.md`.
- **Context**: The user repurposed the Telegram bot token away from the Python long-polling bot to the Claude Code MCP plugin so the same chat could be both the reels-digest entry point and a general universal-remote. Two bots was the obvious alternative.
- **Alternatives**: Two bots (one for reels, one for the universal remote) — rejected: 2× hosting, 2× monitoring, another `@handle` to remember, directly against the consolidation-over-proliferation preference.
- **Consequences**: One bot, one chat surface, one mental model. Reuses the existing FastAPI + SQLite + daily-digest pipeline with no duplication. Telegram intent routing happens in Claude (text matching). The cost: ingestion now depends on a live Claude session — but the universal-remote setup already requires that. `src/telegram_bot.py` stays in the repo for reference only.
- **Date**: 2026-04-27
